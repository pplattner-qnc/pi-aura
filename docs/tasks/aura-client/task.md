## User-visible outcome

An implementation-agnostic `AuraClient` interface lives in
`@pi-aura/shared/aura-client`, with expressive domain types for inputs and
outputs (not the generated types). A concrete `HeyApiAuraClient`
implements it by delegating to `src/generated/` (the `@hey-api/client-fetch`
SDK), mapping domain types <-> generated types internally. A
`createDefaultAuraClient()` factory (in `@pi-aura/shared`) builds the
keyring + reads `settings.json` for the base URL + constructs
`HeyApiAuraClient`. Scripts depend on the `AuraClient` interface; tests
inject a fake.

## User story

As a script (`aura.ts`, `aura-digest.ts`), I want a typed, method-per-verb
Aura client with expressive domain types, backed by the generated REST SDK
and authenticated via the OS keyring, so I can call Aura without the MCP
wrapper and without generated types leaking into my code.

## Scope boundaries

- `AuraClient` interface in `packages/shared/src/aura-client.ts` with
  ~21 methods (today's exercised verbs) and expressive domain types.
- **The generated client moves into `packages/shared/src/generated/`**
  (Wayfinder decision, resolving the open fog): the codegen setup
  (`openapi.yaml`, `openapi-ts.config.ts`, `@hey-api/openapi-ts` devDep,
  the `make codegen` target) moves from `scripts/` into `packages/shared/`.
  `packages/shared` owns the generated client; scripts + the extension import
  it via `@pi-aura/shared/aura-client`. The existing
  `scripts/src/generated/` becomes dead after `call-site-migration` rewires
  callers and is removed in `clients-cleanup`.
- `HeyApiAuraClient` in the same package, delegating to
  `packages/shared/src/generated/` (now in the shared package itself).
- `createDefaultAuraClient()` reads `settings.json` `aura` block (base URL
  via a new `instance`/`baseUrl` field) + builds the keyring via
  `createKeyring()` + reads the PAT via `getSecret({service:"aura",
  name:"pat"})`.
- DI: `HeyApiAuraClient({ keyring, baseUrl })`.
- Does **not** migrate call sites (that's the next task) — only provides the
  interface + impl + factory.

## Acceptance criteria

- `@pi-aura/shared/aura-client` exports the `AuraClient` interface, its
  domain types (e.g. `Artifact`, `TaskListQuery`, `UpdateArtifactInput`,
  `BoardBriefing`, etc.), and `createDefaultAuraClient()`.
- `AuraClient` has ~21 methods matching the exercised verbs (getArtifact,
  mcpUpdateArtifact, mcpCreateArtifact, getKnowledgeNode,
  getKnowledgeNodeByPath, saveKnowledgeNodeBody, mcpWikiSearch,
  getKnowledgeTree, createKnowledgeNode, mcpCreateUploadDocument,
  mcpGetUploadDocument, getBoardBriefing, getBoardSummary,
  listNotifications, getMyPriorityQueue, getMyCapacity, listArtifacts,
  listTasks, getArtifactApprovals, getTaskByHumanKey, getArtifactReview).
- `HeyApiAuraClient` implements `AuraClient` by calling the generated SDK;
  generated types never appear in the `AuraClient` interface signature.
- `createDefaultAuraClient()` returns a working `AuraClient` authenticated
  with the keyring PAT + pointing at the settings base URL.
- `npm run typecheck` passes; a smoke test constructs the client and calls
  one read method against a real Aura instance (or a fake SDK).

## Existing abstractions to use

- `scripts/src/generated/` (the `@hey-api/client-fetch` SDK) — the substrate.
- `@pi-aura/shared/keyring` — for the PAT.
- `scripts/src/settings.ts` (move to `@pi-aura/shared/settings`?) — for the
  base URL; the `aura` block needs a new `instance`/`baseUrl` field (Q4).
- `scripts/src/types.ts` — reference for the Aura response shapes; the
  domain types overlap with these (the migration task dedupes).

## Architecture / domain decisions

From the first grilling: method-per-verb interface, expressive own domain
types mapped to/from generated types (Q8), DI + factory (Q10), base URL
from `settings.json` `aura` block (Q4), PAT from keyring (Q1), ~21 verbs
(Q11).

## Implementation notes

### slice 1 — codegen-move-to-shared (done)

- `@hey-api` codegen setup moved from `scripts/` into `packages/shared/`:
  `openapi/openapi.yaml` + `openapi-ts.config.ts` (input/output repointed to
  `openapi/openapi.yaml` / `src/generated`), `packages/shared/package.json`
  gains `@hey-api/client-fetch@^0.13.1` (dep) + `@hey-api/openapi-ts@^0.64.2`
  (devDep) + a `codegen` script, `packages/shared/.gitignore` gains
  `src/generated/`, and the `Makefile` `codegen`/`gen` targets are repointed
  to `packages/shared` (`install` stays root `npm install`).
- `packages/shared/src/generated/` is gitignored and regenerated by
  `make codegen` (or `cd packages/shared && npm run codegen`); verified:
  `cd packages/shared && npm run typecheck` passes on the generated tree.
- `scripts/src/generated/` + `scripts/openapi*` + `scripts/package.json`
  `@hey-api/*` deps were deliberately left in place (dead after
  `call-site-migration`; removed in `clients-cleanup`).
- **Environment note:** `make` is not on `PATH` on this NixOS machine, so the
  GREEN was verified via `npm run codegen` / `npm run typecheck` in each
  workspace rather than `make codegen` / `make gen`. The `Makefile` targets
  are correct but unverified end-to-end here; a machine with `make` (or CI)
  should run `make gen` once to confirm the target wiring.

### slice 2 — aura-client-interface (done)

- `packages/shared/src/aura-client.ts` exports the `AuraClient` interface
  with exactly 21 methods (4 artifacts + 6 knowledge/wiki + 2 upload +
  2 boards + 1 notifications + 2 my-board + 1 listTasks + 3 reviews) and all
  domain types from the arch spec's "Domain type catalogue" (verified
  field-by-field against the catalogue and cross-checked against
  `scripts/src/types.ts`).
- The interface has **no** imports from `./generated/*` (Q8 satisfied —
  pure hand-written domain types). The `"./aura-client": "./src/aura-client.ts"`
  exports mapping was added to `packages/shared/package.json`.
- **`ListArtifactsInput`** was added as a loose `{ [k: string]: unknown }`
  index-signature type — the arch spec's method-signature section references
  it but the "Domain type catalogue" does not enumerate its fields. The
  call-site-migration task may tighten it.
- **Naming note for `call-site-migration`:** the slice doc's test plan
  references `TaskListQuery`, but the actual exported type is `ListTasksInput`
  (per the arch spec, which is authoritative). The migration task should import
  `ListTasksInput`, not `TaskListQuery`.
- `npm run typecheck` passes in both `packages/shared` and `scripts` (the
  scripts workspace resolves `@pi-aura/shared` types across the workspace
  boundary).
