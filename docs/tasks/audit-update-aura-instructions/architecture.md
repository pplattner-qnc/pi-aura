# Architecture: audit, refresh, and reshape pi-aura

Produced from the stable specification at `docs/tasks/audit-update-aura-instructions/spec.md`; this document is the living architecture from here on, and the specification's architecture content below is archival from this write.

## Problem statement (archival, from the specification)

The package's instruction surfaces teach an Aura server that no longer exists. The aura skill documents a 90-tool server while the live aura-mcp-dev server (build 2026-10-12, commit 4aa37833) exposes 120 tools; the capacity guidance tells agents the capacity MCP tools are gone when three of them are back; the process resources teach a status series and a review flow Aura replaced months ago; the root docs teach a config file shape pi does not read. An agent that follows the shipped instructions is actively misled, not merely underserved.

At the same time the package carries an agent-facing CLI and REST access layer (the bundled CLI, the REST reference document, and the docs that teach them) that the operator is retiring, and two engineering surfaces (the engineering-foundation skill and the engineering-rules extension) whose job has moved to another package. The package must be refreshed and reshaped so that what it ships is true of the live server and carries only the surfaces it still owns.

## Solution (archival, from the specification)

Every instruction surface that survives the reshape teaches the live 120-tool aura-mcp-dev server, MCP-first: the aura skill and its usecase and process resources follow the confirmed placement map and the two-layer citation policy; the root documents carry no stale claim from the audit reports. Of the seven extensions, six survive, and the two that call Aura (the mention machinery and the feedback tool) run their access on the MCP server through a small in-extension client, keeping the sqlite mention cache and its instant-render behavior. The agent-facing CLI and REST surface is removed; the internal REST library is removed when (next to) no in-package consumers remain after the migration, otherwise kept or inlined per the consumer rule. The engineering-foundation skill and the engineering-rules extension move out.

## Implementation decisions (archival, from the specification)

### Instruction surfaces

**The aura skill file.** The rewrite follows the mcp-inventory report's outline: the tool count becomes 120 with the build identity (2026-10-12, commit 4aa37833) cited once; the ten mcp* tools stay listed with three one-line corrections (the new opinion artifact kind replacing review, the base64 upload description with its size limit, the artifact mode renamed to whole with the section and whole-body limits and the expected-version contract); the "left MCP entirely" paragraph becomes a per-capability scorecard (back: the capacity tools, board summary, owner and crew search; half back: Jira and Asana reads, wiki file reads, memory browse plus ingest; still absent: notification writes, the review-turned-opinion flow beyond its listing filter, skills import, wiki upload); the response-format contract is added (compact default, detail on the declaring tools, full on the two task reads; MCP-only, not part of the HTTP API; the permission apparatus excluded from every tier and reachable by the same PAT through REST); the new tool families get bullet-level coverage; threaded comments become flat per the live description; the contradictory capacity sentences are resolved to the current truth; the stale feedback tool-name token is fixed to the current naming. aiSetup and getBlueprintFiles are not documented at all.

**Usecase resources.** The twelve usecase files get their per-file corrections from the usecase-resources worklist under the confirmed placement map: capacity-planning.md is rewritten (the capacity MCP tools are back and documented as the primary path; company capacity settings and the cross-member per-task view are REST-only capabilities and get UI pointers; the placement facts already landed with ticket 4, so the scope semantics remain ticket 8's capacity work); the uuid-to-id parameter sweep lands across the task, signals, wiki, skills, and unified-search files; wiki-knowledge.md documents the frontmatter save contract (identifier plus a raw YAML string or null), version numbering shapes, and file-asset version history; task-management.md gains owner and crew management, the blocked flag, the story-point flow, the priority queue, progress, activity, user groups, repository linking, the workflow variant, and the neighborhood read, and drops its false "no member management on MCP" claim; code-search.md drops its nonexistent parameter and documents the repository-slug format; unified-search.md adds the FEEDBACK source and the mention-candidate tool with correct limit semantics; artifact-management.md documents the opinion_requested filter and the whole-mode replace contract; memory-graph.md corrects the ingest contract (no reason parameter, open questions) and the entity-source result (a navigable route, not provenance); feedback-submission.md gets the triage flow and the fixed tool naming; upload-documents.md lost its verified-current baseline when ticket 4 rewrote it to teach MCP-with-context guidance, so ticket 8 re-verifies its base64 upload description and size limit against the live dump rather than skipping the file.

**Process resources.** The seven process files repoint their canonical references to the replacement wiki pages under the way-of-working section; workflow-phases.md is rewritten to the split status series (resolved by hierarchy level and workflow variant, immutable at creation; the standard series without the two retired statuses; lean series for sagas and subtasks; discovery ending after alignment); capacity.md moves to the new capacity model (the placeholder epic for non-task work, commitment steps, full landing, the daily reset; no structural reserve); review-modes.md teaches opinions as the successor flow (graded scale, no locks or rounds, edit-after-submit) and drops the dead CLI review commands; the quality gates (disciplines, verdicts, the reason requirement to leave a rejected gate) are documented; integrations.md updates the Asana and Jira postures and task parenting; roles, escalation, and the index get header and minor updates.

**Root documents.** README, CONTEXT.md (the glossary), AGENTS.md, docs/testing.md, and docs/dev-env.md take the root-docs worklist: the MCP configuration example moves to the pi-native config file with url plus headers; the install pin tracks the released version; the "no user-facing commands" claim is corrected to name the secrets command and the feedback tool; the unused prerequisites are dropped; the credential story describes the keyring and the settings-derived base URL with the MCP config file as the import source only; the glossary entries for the access client and the keyring describe the post-reshape reality; the dev setup flow describes the post-teardown tree; the testing mock conventions match what the tests actually do; the extension and skill tables lose the moved-out entries; em-dashes are removed from touched prose.

**Citation policy.** Two layers: tool contracts (names, parameters, shapes, limits) cite only the live introspection evidence or the synced spec; semantics and process cite the wiki (the patchnotes for what a facility is, the replacement process pages, the task-artifact conventions page for the story-point scale, tracker-aura for calling discipline minus its two flagged errors). The June repository mirror is never cited as current; chat-only tool names from the skills spaces are never copied into the docs.

### Extensions and the MCP feed (amended at ticket time, see the phase decisions section)

The mention machinery and the feedback tool reach Aura through a typed interface standing on pi's own MCP client library, plus a model-facing server registration owned by the package; details in the contracts below. The sqlite cache keeps its stale-while-revalidate design; the feedback tool keeps its sign-off flow and JSONL record; the prompt-injection extension, the secrets command, and the reachability probe keep their behavior.

### Teardown and the consumer rule

**The agent-facing surface is removed unconditionally:** the bundled CLI, the scripts that only serve it, the REST reference resource, the Taskfile targets that build or regenerate them, and every doc that teaches REST or CLI access to Aura. The six dead review subcommands are removed, not migrated.

**The internal REST library follows the consumer rule:** after the MCP migration lands, the in-package consumers of the generated client and its wrapper are counted. With (next to) none, the library, its spec source, its sync and codegen targets, and its tests are removed, and any straggling call site is inlined. With surviving consumers, the library is either kept whole or its few call sites are inlined, decided by how many there are and how likely they are to need changes when Aura's API changes. The decision is made at implementation time on the counted evidence, not pre-emptively.

**Guards.** The remnants guard that pins removed surfaces is updated to hold the new retirements.

### Move-out of the engineering surfaces

The engineering-foundation skill directory is removed from this package whole, its new home the other package, which becomes the sole delivery vehicle for the engineering canon. The engineering-rules removal landed as a split, not a deletion: the dispatch half (the extension factory, the always-on and on-demand system-prompt section builders, the mention-name collector, the `before_agent_start` body-injection resolver) is deleted, and the loading half (`loadRules`, the `Rule` type and frontmatter parsing, the glob compiler and matcher, the global-plus-project settings union, the recursive `.cursor/rules` walk) survives verbatim, the code identical and the comments adjusted, as `extensions/cursor-rules.ts`, a non-manifest library module with a sibling test, because the reference engine imports `loadRules` and `Rule` for the local-only rule-mention kind and no spec text authorized removing that kind. Rules dispatch and mentioned-rule body injection are now the plugin repo's job, the plugin repo consuming the same `.cursor/rules` directory with its own loader copy; until that dispatch ships, `#rule:` and `@rule:` mentions still autocomplete and expand to `<rule-ref>` elements, but nothing injects the body. The removals update the package manifest (exactly the six surviving extensions, deep-equal pinned by the guard), the README's skill table (the README has no extension table; the engineering-foundation row is dropped), and the project instructions file (its engineering-foundation skill-layout bullet is dropped, and it never carried a rules bullet).

## Phase decisions recorded at ticket time (operator rulings)

These supersede the corresponding archival statements above:

- **Transport reuse.** No transport is hand-rolled. The typed interface stands on `@earendil-works/pi-mcp` (the MCP client library pi itself uses, present in the dependency tree and resolvable inside the pi process where the extensions run), using its client and streamable HTTP transport with the endpoint from settings and the PAT from the keyring.
- **Server registration.** One part of the package registers the model-facing aura-mcp-dev server at extension load from settings plus keyring, silently skipping when no PAT is stored; a user's own configuration entry keeps precedence. The package's own data path uses its own client instance through the typed interface (pi does not expose its live tool connection to extension code); the two connections share the endpoint and the PAT. The README's MCP configuration section becomes an optional-override note.
- **Contract self-check.** On every initialization the typed interface fetches the server's live tool schemas and compares them against the definitions the package ships (derived from the effort's introspection evidence). Cosmetic drift (a new optional parameter, a changed description) warns the user naming the tool and the difference. Core drift (a tool gone, a parameter the interface sends or reads renamed, retyped, or newly required) makes that tool's path unavailable: calls fail fast, the affected machinery degrades to its established cache-only behavior, and the warning names what broke. The shipped definitions are refreshed whenever the package re-audits the server; this check is the drift-detection loop the effort exists to close.
- **Documentation ordering.** The documentation tickets wait for the code tickets; they never describe files still present.
- **Release outside the effort.** The version bump, the changelog entries, and the tag for 0.9.0 happen outside this effort, which supersedes the specification's Release subsection and the map's release-scoped success test. The README install-pin correction stays in the root-documents ticket.

## Per-ticket graph and interface contracts

Ten tickets. Levels (blockers first): the registration-and-interface ticket, the CLI-REST removal, and the engineering move-out can start immediately; the two migrations wait on the interface; the consumer-rule ticket waits on the migrations and the removal; the four documentation tickets wait on all five code tickets. Tickets 1, 4, and 6, the first dependency level, and tickets 2 and 3, the second, have landed; their entries below state the surface that actually shipped, and the pending entries are written against that surface.

**1. aura-mcp-interface (feature, m; blocked by none).** Landed. One manifest entry, `extensions/aura-mcp-server.ts`, registers the model-facing server at extension load from the settings endpoint and the keyring PAT, silently skipping without a stored PAT and also without a base URL (a conservative superset of the no-PAT rule); a user's own mcp.json entry keeps precedence by pi's own user-config rule, not by a pre-check, pinned by a guard that reads pi's source, so a pi upgrade changing the precedence or the session_start wiring fails the suite. The typed interface is two non-manifest library modules: `extensions/aura-mcp-contract.ts` holds the shipped tool contracts, the drift comparison, the server name, and the endpoint derivation as pure data and pure functions (no imports, no I/O), and `extensions/aura-mcp-client.ts` is the typed wrapper over the injectable caller, constructed by `createAuraMcpInterface({ caller?, baseUrl?, pat?, notify? })` with exactly ten typed methods (task search with full-text, archived visibility, paging, sorting; task read by human key; artifact search and read; knowledge search; tree fetch; node reads by identifier and by path; space listing; feedback creation). The contract self-check runs once per construction and compares type, requiredness, enum membership, default, and description; JSON-Schema bounds are deliberately not compared (the exclusion is documented in the module comment), so a tightened bound surfaces only at call time; a failed live fetch is a silent skipped verdict with every path callable and natural errors surfacing on call; cosmetic drift reaches the user only through the injectable `notify` hook or `interface.selfCheck()`. Exports to dependents: the constructor with the caller seam; the per-tool typed methods; `AuraMcpToolUnavailableError`, the degraded-path error the consumers map onto cache-only behavior; `AuraMcpCallError`, covering both caller-level rejections (transport, protocol, timeout, the cause preserved) and application errors inside HTTP 200 (isError results); the contract data (tool names, the server name, the endpoint derivation) re-exported from `aura-mcp-contract.ts`; registration that survives absent credentials. Guards: no static pi-mcp import and no JSON-RPC wire literals in the three modules; no new runtime dependency (the manifest gains no dependencies block); the shipped contracts provenance-checked against the effort's introspection dump.

## Do-not-reimplement notes

- No hand-rolled JSON-RPC, no envelope building, no reconnect logic: pi's MCP library owns all of it (landed and pinned: no static pi-mcp import and no JSON-RPC wire literals in the three interface modules).
- No second symlink of the model-facing registration: one registration (`extensions/aura-mcp-server.ts`), and it yields to the user's own configuration by pi's own precedence rule, not by a pre-check (a guard reads pi's source, so a pi upgrade changing the precedence or the session_start wiring fails the suite).
- The sqlite cache is not rebuilt; the rendering contract (one render per keystroke, cache-first, late resolutions dropped) is unchanged.
- The typed REST client is not regenerated anywhere in this effort; the consumer-rule ticket only removes or preserves it.
- No new runtime npm dependencies: the pi-process modules resolve the way the existing extension imports do (dynamic-import seam; landed and pinned: the manifest gains no dependencies block).
- The engineering-rules dispatch does not come back: `extensions/cursor-rules.ts` stays loading-only, and rules dispatch plus mentioned-rule body injection are the plugin repo's job, not this package's.
- The landed self-check semantics stand as shipped: once per construction, a failed live fetch is a silent skipped verdict (a server unreachable at init produces no drift signal), and JSON-Schema bounds are not compared. Dependents surface drift through the notify hook rather than new machinery.

## Seams

- **The caller seam**: the typed wrapper takes an injectable caller plus an injectable `notify` hook; tests assert envelopes, degraded-path errors, and the self-check verdicts against fakes, and without a notify hook cosmetic drift is observable only through `interface.selfCheck()`. The landed consumers sit one level up: every mention adapter takes `createInterface: () => Promise<AuraMcpInterface>` (one shared construction per session), and the two extension factories expose their own injection hooks (`loadCredentials` and `createCache` on the reference engine, `loadCredentials`, `createInterface`, and `logPath` on the feedback tool), production-wired by default; the reference engine's `/reload` connection release is pi-runtime verified only, with no suite coverage.
- **The credential seam**: the registration, the reference engine's `session_start` construction, and the feedback tool's per-submission construction all read settings plus keyring through the shared exported loader (`loadAuraMcpCredentials`) over the existing dynamic-import seams; tests use the fake keyring and settings fixtures, and the reference engine's construction-path regression drives the real loader (a tmp settings file, a recording fake keyring) with the default pi-mcp caller over loopback HTTP.
- **The degrade seam**: a core-drift unavailable path surfaces as `AuraMcpToolUnavailableError` and a call failure as `AuraMcpCallError` (caller-level rejections: transport, protocol, timeout, the cause preserved; plus application errors inside HTTP 200). The landed consumers map them differently: the reference engine degrades cache-only on any failure through a uniform catch (a behavioral superset: it never imports the classes by name, and a failed construction lands in the same never-blocking path), while the feedback tool keeps dedicated fail-fast wording for the unavailable case and one generic text for the call failures.
- **The evidence seam**: each documentation ticket works from its planning task's recorded worklist, not from re-derivation; the worklist baselines ticket 4 already changed (upload-documents.md, the two capacity files, testing.md, dev-env.md) are recorded in the ticket entries, and the two migration landings are recorded in their entries too (the wiki version as resolution-time data, every tree node a candidate, the space-listed warmup, the feedback tool's per-submission interface lifetime, the two test-fixture imports), which the documentation tickets state as fact.
- **The guard seam**: removed names and retired claims are pinned by tests, so regressions fail the suite rather than a review; the consolidated guard also pins what was deliberately kept (the Taskfile targets, the manifest's six extensions) and carries the teaching scan's deliberate exceptions, so sanctioned phrasings do not fail the suite; and the landed migrations pin their own truths test-side (the deep-equal envelope assertions on the corrected live-wire parameters, the drifted-`listTools` degradation fake, the no-caller construction-path regression, the feedback module's no-REST-import pin).
