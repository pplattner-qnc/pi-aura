## Deviation report: mention-machinery-mcp

Baseline note: no `task/mention-machinery-mcp` branch exists yet (the land step cuts it), so the prescribed `task/..` diff cannot run. The implementation branch `ticket/mention-machinery-mcp` is nine commits cut from `develop` at 5d42494, which is both develop's tip and the merge-base (verified), so the reviewed diff is `git diff develop...ticket/mention-machinery-mcp`. It touches exactly two files, `extensions/aura-references.ts` and `extensions/aura-references.test.ts`; the three landed interface modules, the package manifest, and the sqlite cache module are untouched. Every claim below was re-verified in this session against the diff and the source, not taken from the implementer's notes: 178 shared tests (43 suites, 0 fail), all ten extension suites green, typecheck clean, and no em-dashes in the touched files.

### API surface changes

- **Adapter seam renamed to the typed interface; exported REST-client types removed.**
  - **Planned:** the architecture prescribes constructing the typed interface with `createAuraMcpInterface`, passing the `notify` hook so the user sees cosmetic drift, mapping `AuraMcpToolUnavailableError` onto cache-only degradation, treating `AuraMcpCallError` as covering both caller-level rejections and in-200 application errors, and taking the tool names and the endpoint derivation from `extensions/aura-mcp-contract.ts`. It says nothing about the adapters' injection seam, which on `develop` was `createClient: () => Promise<TaskAuraClient & ArtifactAuraClient & WikiAuraClient>` backed by the dynamic `createDefaultAuraClient` import from `@pi-aura/shared/aura-client`.
  - **Actual:** every server kind adapter now takes `createInterface: () => Promise<AuraMcpInterface>`; the factory builds one interface per `session_start` behind a shared accessor (notify wired to `ctx.ui.notify`; the accessor rejects before the first `session_start`). The exports `TaskListQuery`, `TaskAuraClient`, `ArtifactAuraClient`, `WikiAuraClient` and the constants `WARMUP_WIKI_SEED_QUERY`, `WARMUP_WIKI_SEARCH_LIMIT` are deleted; a repo-wide grep finds no remaining consumer of any of them. Aura access goes only through the ten typed methods plus `auraMcpJson`. The drift-error mapping is a behavioral superset of the spec: `AuraMcpToolUnavailableError` and `AuraMcpCallError` are not imported by name; the adapters degrade on any failure through a uniform catch, which covers both classes (and the construction rejection) and keeps the pane cache-only and never-blocking. The degraded behavior is pinned by a drifted-`listTools` fake (the self-check marks the listTasks path unavailable; `callToolHits === 0`).
  - **Impact:** package-internal (`aura-reference-cache.ts` imports only the cache types it always did; the no-remnants guard still passes). Ticket 5 (rest-library-consumer-rule) counts one fewer consumer family: the reference engine no longer imports `@pi-aura/shared/aura-client` at all (`extensions/aura-feedback.ts` remains a consumer until ticket 3 lands). The documentation tickets describe the seam as it now ships.

- **Wiki items are versionless until resolution, and the resolved version is never written back.**
  - **Planned:** the ticket says "versions load lazily from the node read when a reference is inserted or resolved" (the architecture: "versions loaded lazily from the node read"). The pre-ticket design carried `version: number` on every wiki row because the old fat tree returned `latest_version`; the live slim tree does not, which is half of why the old walk never populated a row.
  - **Actual:** `WikiReferenceItem.version` is optional; every tree-derived row (warmup and the search-hit join alike) carries no version. The `wikiItemMetadata` completeness gate (space plus path plus version) falls a versionless row through to the node read, so expanding a cache-held wiki mention always costs one node read: the path form via `getKnowledgeNodeByPath`, the uuid form via `getKnowledgeNode` plus the memoized tree join. No `cache.write` exists on the resolution path (the only write sites are the SWR merge and the three warmups), so a page mentioned in two prompts costs two node reads. Insertion (autocomplete selection) triggers no fetch, the sensible reading of the ticket phrase, but the phrase does read as if the insert path could load a version too.
  - **Impact:** server-call volume per wiki expansion, not render behavior: the reference tags, titles, and statuses are unchanged and the version always resolves from the fresh node read. The documentation tickets should state the wiki version as resolution-time data, never as cached-row data.

- **Wiki warmup replaced: the search-seeded probe becomes a space listing.**
  - **Planned:** the ticket itself mandates this ("the 'no space-listing verb' premise drops; the listing exists"), so the mechanism is spec-conformant; recorded because the seed-query design (one generic `"der"` search bounded at 50 whose hits picked the spaces to cover) is what `develop` shipped.
  - **Actual:** the warmup calls `listKnowledgeSpaces()` once, then fetches one memoized tree per listed space, writing each space capped at `MAX_WIKI_ITEMS_PER_SPACE` (500, unchanged). Tests cover the listing, one tree per space, the cap in tree order, aborts between spaces, and a failing listing or failing per-space tree.
  - **Impact:** full readable-space coverage replaces hit-space coverage; warmup cost goes from one search plus one tree per hit space to one listing plus one tree per listed space. No dependent ticket observes it beyond documentation.

- **Every tree node is a wiki candidate (the DOCUMENT filter is gone).**
  - **Planned:** the ticket says candidates derive from title and slug over the slim shape. The old walk filtered `node.kind === "DOCUMENT"` on a field the live tree no longer returns (the other half of the never-populated bug).
  - **Actual:** `wikiItemsFromTree` pushes every node, so folders (and file assets, if any ride the tree) appear as autocomplete candidates. Resolution discriminates: the by-path node read is assumed to resolve documents only, so a folder mention stays as typed on submit. `source_path` exists on the slim node type as documentation of the live shape but is not used as a discriminator.
  - **Impact:** user-visible candidate set. The documents-only assumption for the by-path read is unverified against a live instance (none is reachable from this environment); excluding folders would need a live probe to find a discriminator. Flagged as a residual risk.

- **The factory owns the interface lifecycle, including a `/reload` connection release.**
  - **Planned:** the architecture covers construction (once, with the notify hook) but not connection lifecycle; nothing in the ticket text asks for a close.
  - **Actual:** the interface is one per session behind the accessor; the SWR refresh gate, the expansion gate (`clientAvailable`), and the warmup probe all latch on the construction outcome; and on a re-emitted `session_start` the previous session's interface is released with a fire-and-forget `ai.close()` (a failed close is swallowed; an in-flight old-session lookup degrades to cache-only through its own catch). Commit b4576f5 added this with no test coverage; the factory is pi-runtime verified only.
  - **Impact:** lifecycle hygiene the migration makes necessary (the typed interface holds one connection where the replaced REST client was per-call); no dependent ticket observes it. The untested lines are a small residual risk.

Everything else is per spec, each point pinned by tests over the fake caller: the task search sends only live-accepted parameters (deep-equal envelope assertions: `{ q, archived: "all", limit, sort_by: "updated_at", sort_dir: "desc" }` per keystroke refresh and `{ archived: "all", limit: 100, page, sort_by, sort_dir }` per warmup page; the stale `search` and `status` keys are gone), artifact search and resolution ride `searchArtifacts`/`getArtifact` with the parameters that were already aligned, wiki search rides `searchKnowledge` with the per-space tree join, both wiki identity forms resolve through the shape-appropriate node read, the reference instruction's artifact kind set is the live one (PLAN, OPINION, GENERIC, plus the chat-only TEMPORARY; REVIEW gone), the local rule kind keeps its `loadRules`/`Rule` imports from `extensions/cursor-rules.ts` (untouched, still loading-only under its module-surface pin), and the rendered output contract plus the strict cache-first render behavior are unchanged.

### Abstraction usage

Tool names and the endpoint derivation reach the engine transitively through `aura-mcp-client.ts` and `aura-mcp-contract.ts`; no tool name appears as a call literal in the engine (comments only), and the three interface modules are untouched by the diff. - Nothing else: the diff touches exactly `extensions/aura-references.ts` and `extensions/aura-references.test.ts`, and the branch carries no other file.

### Addendum: the route-back run (construction-path fix)

The first verification of this ticket returned NOT VERIFIED with a production blocker: the factory constructed `createAuraMcpInterface({ notify })` with no credentials, so the default caller resolved the connection from its (empty) arguments, `resolveAuraMcpConnection` threw on the missing PAT, and the rejection latched `clientAvailable` false for every real session: no warmup, no SWR refresh, every mention kind cache-only for every user. The suites stayed green because they inject fake callers at the adapter seam and never exercised the default construction. The claims in the sections above stand for the adapter seam; this addendum records the fix and supersedes the construction-path picture they imply.

- **The fix (in the engine's construction path, per the route-back):** the `session_start` handler now loads the real credentials through the exported loader (`loadAuraMcpCredentials`, the package's dynamic-import seams over settings and keyring, the same read the registration extension performs) and passes `baseUrl` and `pat` into `createAuraMcpInterface` beside `notify`. With credentials present the construction derives the endpoint from `aura.baseUrl`, authenticates with the keyring PAT, and runs the contract self-check; the session's gates (refresh, expansion, warmup) arm from its success. Without credentials the behavior is exactly the documented degrade: a broken loader read degrades to the empty credential set, the construction rejects into the existing catch, and the gates stay off for the session (a `/reload` re-arms). The three landed interface modules are still untouched.

- **Two factory hooks (`AuraReferencesExtensionOptions`, API addition):** `loadCredentials` (defaults to the real loader) and `createCache` (defaults to the real sqlite-backed `createSessionCache`), the registration extension's hook pattern mirrored. The cache hook exists so the regression test never touches the real settings file or the real `~/.pi/agent` sqlite store; production wiring passes nothing and behaves as before.

- **The construction-path regression test:** drives the factory's `session_start` with NO injected caller anywhere.
