## End-to-end behavior

The agent (or a human) can browse the full Aura REST surface *by
operationId* without parsing YAML at runtime. `node aura.mjs rest list`
prints every operation in `openapi.yaml` grouped by tag, each with
`operationId`, method, path, and a one-line summary. `node aura.mjs rest
describe <operationId>` prints the full shape of one operation: method,
path, path params, query params (name, required, schema), request body
shape, and response codes. A generated Markdown resource
(`skills/core/aura/resources/rest-api.md`) lists the same operations with
their parameters and is committed; it is regenerated by a new `gen-rest-doc`
build step so it never drifts from the spec.

This is the first vertical slice of the `rest` command group: it stands up
the OpenAPI loader (the single source of truth every later slice reuses),
the two read-only browse subcommands, and the generated reference resource.
It is independently verifiable (the AC reads the CLI output + the committed
markdown) and delivers real value on its own.

## What this slice delivers

- An **OpenAPI loader** in `@pi-aura/shared`
  (`packages/shared/src/openapi/loader.ts`, exported via the shared `exports`
  map as `@pi-aura/shared/openapi`) that parses
  `packages/shared/openapi/openapi.yaml` once into an in-memory **operation
  index**: `Record<operationId, { method, path, pathParams, queryParams,
  bodyShape, tags, summary, description, responses }>`.
  - Resolves only the `$ref` constructs the Aura spec actually uses
    (`#/components/schemas/...`, `#/components/parameters/...`,
    `#/components/responses/...`); **fails loudly** with the ref path if an
    unsupported construct is hit (no silent skipping).
  - Path params are extracted from the path template (`{uuid}`) and
    cross-checked against the `in: path` parameters.
  - Cached per process (parse once).
- A **`rest list`** subcommand in `scripts/src/aura.ts`: prints operations
  grouped by tag (alphabetical within group), each line
  `operationId  METHOD  /path  — summary`. No truncation. Unknown tag
  (operation with no tags) grouped under `Other`.
- A **`rest describe <operationId>`** subcommand: prints method, path, each
  path param (name, required, schema type), each query param (name,
  required, schema), the request body shape (content type + referenced
  schema name or inline shape), and the response codes with their
  descriptions. Unknown `operationId` → clear error listing the closest
  matches (simple substring/Levenshtein from the loader's id list; the
  proper search index arrives in slice 3).
- A **generated Markdown resource** `skills/core/aura/resources/rest-api.md`
  listing all operations with their parameters, grouped by tag, produced by
  a generator run at build time.
- A **`gen-rest-doc`** build step wired into `Taskfile.yml`'s `build`
  target (before the esbuild bundle) that runs the generator from
  `openapi.yaml` and writes `resources/rest-api.md`. `make`/`task build`
  regenerates it; the file is committed.
- The `USAGE` block in `scripts/src/aura.ts` gains the `rest list` and
  `rest describe` lines.

## Acceptance criteria

- `node aura.mjs rest list` prints all ~273 operations grouped by tag, each
  with `operationId`, method, path, summary — no truncation, no operation
  omitted.
- `node aura.mjs rest describe updateTaskMemberCapacity` prints path
  `/tasks/{uuid}/members/{userIdOrUuid}/capacity`, method `PATCH`, path
  params `uuid` (uuid) and `userIdOrUuid` (string), the request body
  referencing `TaskMemberCapacityUpdate`, and response codes 200/400/401/
  403/404/500.
- An unknown `operationId` to `rest describe` prints a clear error naming
  the id and listing the closest matches.
- `skills/core/aura/resources/rest-api.md` exists, is committed, contains
  `updateTaskMemberCapacity` under the `Capacity` group with its params, and
  is byte-identical when regenerated twice (`task build` twice → no diff).
- `task build` regenerates `resources/rest-api.md` (the `gen-rest-doc` step
  runs and the file is up to date after build).
- `task typecheck` passes for both `scripts` and `packages/shared`.
- The loader's test suite (loader + serializer-adjacent parsing) passes under
  `tsx --test` in `packages/shared`.

## Test plan

### Seams (test only at these)
- `@pi-aura/shared/openapi` `loadOpenApi(path)` → operation index (pure,
  file-based; no network).
- `rest list` / `rest describe` → stdout (run the CLI dispatch with a
  fake `process.argv` against a small fixture OpenAPI file; assert stdout).
- The `gen-rest-doc` generator → markdown string (pure function over a
  parsed index; assert output contains expected operations/params).

### Failure modes / edge cases
- OpenAPI with an unsupported `$ref` (e.g. a remote URL ref) → loader
  throws a loud error naming the ref path (tested with a fixture).
- Operation with no `tags` → grouped under `Other` in `rest list` and in
  `rest-api.md`.
- Operation with no `operationId` → loader skips it with a loud warning
  naming method+path (the generic invoker keys on `operationId`; an op
  without one is unusable and should not silently fail later). Tested with
  a fixture.
- Path with multiple params (`/a/{x}/b/{y}`) → both parsed as path params.
- Duplicate `operationId` across the spec → loader throws (loud, names both
  method+path).
- Unknown `operationId` in `describe` → lists closest matches, exit code 2.

### Scenarios
- Fixture OpenAPI with 3 ops across 2 tags → `rest list` output matches
  expected grouped text.
- `describe` on a POST with a request body → body shape section printed.
- `describe` on a GET with query params → query section printed with
  required flags.
- `gen-rest-doc` on the real `openapi.yaml` → output contains the capacity
  op + a representative artifact op.

## Constraints and dependencies

- **Single source of truth:** the loader is the only thing that parses
  `openapi.yaml`. `rest list`/`describe` and the `gen-rest-doc` generator all
  consume the loader's index. Do not duplicate YAML parsing.
- **Workdir-free inline results:** `rest list`/`describe` print inline to
  stdout (the existing `aura.ts` style for read commands); they do NOT use
  the workdir model.
- **No network, no auth** in this slice: `list`/`describe` are pure
  metadata; the invoker (slice 2) is where auth + fetch enter.
- **Runtime metadata path (DECIDED — see task Architecture notes):** the
  parsed operation index is **not** inlined into the bundle in this slice.
  Slice 1 reads `openapi.yaml` at runtime via a path resolved relative to the
  shared package / repo layout (the loader takes an explicit path argument,
  defaulted to `packages/shared/openapi/openapi.yaml`). Slice 3 will inline
  a compact metadata blob into the bundle for the self-contained end-user
  CLI; until then, list/describe are developer-facing and read the YAML.
  This keeps slice 1 focused on parsing + rendering and avoids coupling to
  the bundler early.
- Reuse the existing `fail()` / USAGE pattern in `scripts/src/aura.ts`;
  add a `rest` group branch to the `main()` dispatch (alongside
  `artifact`/`wiki`/`upload`).
- `js-yaml` is already a `scripts` dependency; add it to `packages/shared`
  deps if the loader lives there (it should — both the CLI and the build
  generator consume it).
- Do NOT implement `rest call`, `rest search`, the code-side tags, the FTS
  index, or the embedding leg here — those are later slices. The loader's
  index shape must be rich enough to support them (so include body shape,
  tags, summary, description) but the later slices own wiring them up.
