- **Actual:** All of that landed as specified, and the load-bearing claims verify against the planning evidence row by row: the count and build identity appear exactly once; the three corrected one-liners match the dump (OPINION with chat-only TEMPORARY qualified, "ingest a file from base64 content" with the 10 MB cap, `section`/`whole` with 50,000/200,000 characters); every scorecard tool name and parenthetical resolves in the dump (including `createRoadmapGoal`'s "Leadership/Admin only" and `systemHealth`'s build-identity line); the response-format section matches the server instructions' contract, with the permission-apparatus list compressed by "and kin" over the server's longer enumeration; the family bullets match the placement map's SKILL.md rows (roadmap goals, tags, projects, comments, glossary, systemHealth) with story points and user groups as one-line entries pointing at their usecase home; the drift table's rows are all addressed (sections 1.1 through 1.5 and the three contradictions of section 6), with the unaddressed-rows criterion holding. What the spec did not spell out, and the implementation did:
  1. The tool-name prefix sentence was rewritten. The drift table's verdict on the old claim ("All tools are prefixed with `aura_2d_mcp_2d_dev_`") was "current (names), prefix rendering inferred"; the ticket named no change to it. The file now says "In pi's tool list every tool carries the `mcp__aura_mcp_dev__` prefix; this page lists the short names." The change was forced by internal consistency: the corrected feedback tool naming (a named ticket row) is pi's rendering, and the old prefix token would have contradicted the file's own feedback section two screens later.
  2. The "Development process" paragraph was reworded. The drift table marked the old flat series ("Open through Done") current against the `updateTask` status enum; the ticket named no change. The file now says "a level- and variant-resolved status series with defined roles, capacity rules, and quality gates", deferring the concrete series to the process resources. Rationale: the process-resources planning record (the split status series by hierarchy level and workflow variant, the v18 quality gates that replaced review gates) supersedes the enum-subset reading, and the old "review gates" wording taught the retired flow the effort removes.
  3. The `mcpUpdateArtifact` one-liner documents one element beyond the ticket's three named corrections: the `confirm_full_replace` destructive-replace gate. The addition comes from the same drift row (the dump's declaration names it beside the limits and the merge base), so the one-liner matches the live declaration more completely, not less.
  4. The response-format REST note omits the server's own example endpoint. The verbatim server instructions carry "(e.g. GET /api/tasks/{id})", and the dump's `mcpUpdateArtifact` description suggests "PATCH /api/mcp/artifacts/{id} from a file with an MCP PAT"; the skill file says only "the same PAT reaches those fields through REST" and names neither endpoint. This is the compliant reading of the ticket's "at most a non-teaching note" and criterion 3, recorded here because it is a deliberate departure from the verbatim contract text the two-layer citation policy cites.
  5. The `mcpCreateUploadDocument` one-liner drops the artifact-creation half of the old wording. The drift table's verdict was "stale (description changed)" with whether an artifact is still created not determinable from introspection (a recorded open item in section 10 of the report); the new one-liner teaches only the base64 ingest with the 10 MB limit and asserts nothing about artifact creation, which is the only wording the evidence supports.
  6. A guard block was added. The ticket and the arch ticket 7 entry name no tests; `packages/shared/test/guards/no-remnants.test.ts` gains a describe block with eight content guards pinning the count and build identity (exactly once), the mcp* list and kind list, the scorecard tiers and tool names, the response-format contract, the flat comments and fixed naming, the codemode pattern, the absence of the two expected-dead tools, and the em-dash ban.
- **Impact:** No dependent ticket consumed a changed contract: the scorecard, the response-format tiers, the mcp* corrections, and the kind list all match what tickets 8, 9, and 10 were planned against, and the export criterion holds (the skill surface the usecase resources hang off). Three handoffs materialize. First, the prefix sentence now makes a claim about pi (its tool-name rendering), not about the server; the drift report marks that rendering inferred, so a pi upgrade changing the rendering stales the sentence, and the guard pins the token so the drift fails the suite rather than passing silently. Second, the development-process paragraph now leans on ticket 9's `workflow-phases.md` rewrite to deliver the concrete split series the sentence defers to. Third, the codemode bullet points at `resources/usecases/artifact-management.md` for the full walkthrough, which is ticket 8's worklist item; until ticket 8 lands, the pointed file does not yet teach the pattern, and the usecase table's row label still reads "review" (an index label, not the skill file's own claim).
